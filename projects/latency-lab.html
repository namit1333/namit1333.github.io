Latency Lab

A stopwatch for software that counts the waits most measuring tools quietly hide.

See the code on GitHub ↗ ← Back to all projects

The problem, in plain words

Speed checks usually work like this: send a request, wait for the answer, write down how long it took. It sounds fair. It isn’t.

When a busy service gets overwhelmed, requests pile up in a queue. The stopwatch only starts once a request finally gets sent — so the ones stuck waiting in line are never timed at all. The report comes back looking fine while real people stare at a spinner.

That blind spot has a technical name, but you don’t need the name to see the problem: a tool that times only what it managed to send will always report a better experience than anyone actually had.

What it does

  1. It plans the crowd.Requests arrive on a schedule, the way real visitors do — steady or randomly spread out, in phases you choose.
  2. It starts the clock when the request should have started.Waiting in the queue counts as waiting, because that is what a person experiences.
  3. It remembers what it had to drop.If a request couldn’t be sent on time, it’s recorded as dropped and given the delay it would have suffered — never quietly thrown away.
  4. It shows both numbers, side by side.The ordinary measurement next to the honest one. The distance between the two columns is exactly the stall the ordinary number can’t express.

In everyday terms

Picture a restaurant timing only the tables that got seated. Latency Lab times every table — including the ones still waiting at the door.

Why it matters

Every website and online service has busy moments: a product launch, a ticket sale, an ordinary Monday morning. Those are exactly the moments ordinary speed checks flatter, and exactly the moments when slow means lost patience, lost sales, and lost trust.

Who it’s for: anyone responsible for a website or service who wants an honest answer to “how slow did it really get?” — and wants that answer readable by a person, not just a machine.

Where it stands

Latency Lab works today and runs from the command line. It was built with engineers in mind, but its reports are designed to be readable by anyone who needs to know how a service behaved under pressure.

Good to know

  • It’s a measuring tool: it never changes the service it tests.
  • The ordinary and corrected numbers are always shown together, so you can see the difference yourself.
  • Runs are repeatable: the same settings produce the same schedule, so results can be checked.
